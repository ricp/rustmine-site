The question behind the work
Can a Rust rewrite keep what people rely on?

I’m testing real workflows against Redmine’s behavior while keeping its existing data. Speed and hosting savings still need a fair comparison.

Personal experiment · not yet for customer installations
Why I started

I love Redmine. I also want it to be faster.

Years of real work

I’ve been working with Ruby on Rails since 2005, and I still use it today. I’ve used Redmine since version 0.4.0, released on 2 January 2007. I like both. I use Redmine to manage real projects for myself and customers, so I know what a rewrite could lose if it gets the details wrong.

Performance is one reason I started RustMine. I’m rebuilding Redmine’s core in Rust to find out whether it can run faster and use fewer resources, while keeping the behavior and existing data people rely on.

This year, my hosting costs have almost doubled for the same service. I’m not paying for more resources. I’m paying more for what I already had.

Some of my customers have worked with me for over a decade. I built their Ruby on Rails applications over those years, and they are feeling the pressure of hosting costs too. I feel responsible for exploring whether I can help.

An experiment to measure

RustMine gives me a substantial project on which to measure what changes when the same work runs in a Rust implementation. I do not have those measurements yet, so I cannot promise lower costs or offer a migration path. I want to find out what the evidence supports.

How the work evolved

I wanted a feature-based rewrite from the beginning. We started with small experiments around Redmine’s tests, its database, and a few API calls. That gave us a way to check our work, but progress felt slow.

We then made the work items larger and more useful: not just reading an issue category, but completing a task such as creating an issue or copying a project. The tests stayed. What changed was what we asked the agents to build next.

RustMine is my private experiment, not a customer commission or a product I can offer today. I have not decided whether to release the source.

The promise I’m testing

Keep the data.
Change the application.

RustMine is designed to work with an existing Redmine core database. The goal is to keep your project history and data, without migrating them to a new system.

How I check the work

Redmine is the reference. For each task we rebuild, I want to know what a person can do in Redmine and whether RustMine does the same thing.

01

Read the Redmine 7.0.2 code and try the task: what does the user see, who is allowed to do it, and what data changes?

02

Use the relevant original Ruby tests to find details that a feature description might miss.

03

Try it in both apps

Give Redmine and RustMine matching sample data. Compare the pages, permissions, files, and saved results.

04

Review the result

Check the covered behavior, permissions, and saved data across the supported databases before I accept the change.

Features and architecture

Redmine gets a lot done through Rails. Its application code is only part of the implementation. Rails supplies capabilities that do not appear when you count Redmine’s own source lines.

With RustMine, I’m trying to reproduce the features and behavior people rely on, including how their data and permissions work. I’m not trying to reproduce Redmine’s Ruby and Rails architecture. Rebuilding Rails just to rebuild Redmine would miss the point.

RustMine has Rust dependencies too, and a different architecture changes where implementation code lives. That does not mean every additional line is justified. A raw application line count is a poor scorecard. Completeness needs tested workflows. Efficiency needs a fair measurement. Neither comes from counting lines.

After the first portMy plan

Then I have to maintain it.

Redmine will keep changing. If this rewrite works, RustMine will need to follow those changes deliberately.

  1. Follow Redmine releases and security notices. Work that has not shipped can be a clue, but it is not a change to copy yet.
  2. For each release, find the changes users will notice and check whether they affect permissions, files, or saved data.
  3. Add tests for those changes, then update RustMine’s behavior where needed.
  4. Review the result, test it with the supported databases, and check existing data before making a RustMine release.

Watch regularly. Ship deliberately.

I would review security fixes quickly, but a new Redmine change should not automatically change RustMine. Surprise software updates are rarely anyone’s favorite kind of surprise.

The resource question

Less hosting cost?
Prove it first.

I want to know whether RustMine can handle the same work faster or with less memory. That might reduce hosting cost, but I have not run a fair comparison yet. I cannot claim a speedup or savings.

How I would compare them
  • Give Redmine and RustMine the same data and the same everyday tasks.
  • Run them on comparable computers and expect the same quality of service.
  • Measure response time, how much work they handle, memory use, and hosting cost.

Choosing a faster language starts the experiment. It does not finish it.
